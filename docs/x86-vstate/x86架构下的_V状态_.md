# x86架构下的"V状态"

## x86 向量扩展状态的组织方式

### 1\.1 统一状态区域：XSAVE Area

x86\-64 架构未采用类似 RISC\-V "标量浮点/向量分别管理"的方式，而是将 x87 浮点、SSE、AVX、AVX\-512 等所有扩展处理器状态，统一组织进一块连续内存区域——XSAVE Area，由 `XSAVE`/`XSAVEOPT`/`XSAVES` 指令统一执行保存，`XRSTOR`/`XRSTORS` 统一执行恢复。区域结构：

```Bash
偏移 0   ~ 511  : Legacy Region（x87 + MMX + SSE/XMM）
偏移 512 ~ 575  : XSAVE Header（含 XSTATE_BV / XCOMP_BV 位图）
偏移 576 ~ ...  : Extended Region（AVX YMM 高位、AVX-512 opmask/ZMM 等）
```

### 1\.2 状态分量（State Component）编号

与向量扩展直接相关的状态分量及其在 `XSTATE_BV` 位图中的编号：

与 RISC\-V V 扩展（RVV）地位对等的，是 bit 2、5、6、7（即掩码 `0xe4`），这几个分量是向量扩展，而 bit 0/1 是架构基线，不纳入统计口径。

`XSAVE`/`XSAVEOPT`/`XSAVES` 执行时，处理器根据内部维护的隐藏追踪位（Intel SDM 13\.6 节称为 XINUSE：每个状态分量一位，记录该分量自上次加载初始配置以来是否被写过），将其值写出到内存中的 `XSTATE_BV` 字段。该追踪位不是软件可直接读写的架构寄存器，只能通过执行保存指令、观察其写出的 `XSTATE_BV` 间接得知。

## 判定逻辑：如何界定"发生了一次向量状态保存"

只要 `save_fpregs_to_fpstate()`（ XSAVES 指令）针对某线程被调用，且调用完成后该线程 XSAVE Header 中的 `XSTATE_BV` 在 bit 2/5/6/7 中至少一位为 1，即计为一次"向量状态切换事件"。

需要说明的是：

- `XSTATE_BV` 中某分量为 1，表示该分量自上次加载初始配置以来"曾经被使用过"，硬件不会在每次调度切换时自动将其清零，清零仅发生在重新加载初始配置，如 `exec()` 后的新 fpstate，或执行 `VZEROALL`/`VZEROUPPER` 主动清空寄存器内容时。

    `VZEROUPPER`是编译器生成AVX/AVX\-512代码时的常见做法：一段256/512位向量代码执行完、即将返回到可能只用SSE的调用者之前，编译器会自动插入这条指令，清空YMM高128位和ZMM0\-15的高256位——这是为了规避：AVX指令后紧跟SSE指令、且高位数据"状态不明确"时，会触发额外几十个周期的开销。

- 但无论该标记是否属于历史遗留，`save_fpregs_to_fpstate()` 这一函数调用本身，代表的是**内核确实执行了一次针对该线程扩展状态的保存动作**。

```Bash

    │   调度器主函数
    ▼
context_switch()                                                kernel/sched/core.c
    │   准备切换上下文
    ▼
switch_to(prev, next, prev)    宏定义
    │
    ├─▶ __switch_to_asm()                                       arch/x86/entry/entry_64.S
    │       纯汇编，切换内核栈指针、callee-saved通用寄存器
    │       （这部分跟FPU/向量状态无关，是GPR层面的切换）
    │
    └─▶ __switch_to(prev_p, next_p)                     arch/x86/kernel/process_64.c:610
            │   标注了 __notrace_funcgraph，"Kprobes not supported here."
            │   "Set the probe on schedule instead."
            ▼
        switch_fpu(prev_p, cpu)                         arch/x86/include/asm/fpu/sched.h:29
            │   static inline
            │   在此处做三个判断：
            │     - !TIF_NEED_FPU_LOAD（这个任务的状态还没被判定为"待重载"）
            │     - X86_FEATURE_FPU 存在
            │     - prev_p 不是内核线程/内核worker
            ▼
        save_fpregs_to_fpstate(old_fpu)                   arch/x86/kernel/fpu/core.c
            │   有独立符号，bpftrace脚本挂载处
            │     - use_xsave() 为真 → 走 XSAVE 系列（下面这条主线）
            │     - 否则 use_fxsr() → 走 fxsave（老CPU兼容路径）
            │     - 否则 → 走 fnsave/frstor（最老遗留路径）
            ▼
        os_xsave(fpu->fpstate)                         arch/x86/kernel/fpu/xstate.h
            │   static inline，准备好 lmask/hmask（要保存的分量掩码）
            ▼
        XSTATE_XSAVE(&fpstate->regs.xsave, lmask, hmask, err)  arch/x86/kernel/fpu/xstate.h
            │   宏，展开为 asm volatile 内联汇编
            ▼
        ALTERNATIVE_3(XSAVE, XSAVEOPT, ..., XSAVEC, ..., XSAVES, ...)
            │   编译期生成4条候选指令+补丁元数据，
            │   开机时 apply_alternatives() 已经把这个位置的机器码
            │   物理改写成这台CPU实际支持的最高档指令
            ▼
        xsave64 / xsaveopt64 / xsavec64 / xsaves64   %[xa]     ← 最终落地执行的裸指令

```

## 观测方法与实现

### 4\.1 挂载点选择

调用链：

```Bash
__schedule()
  → trace_sched_switch()          （tracepoint 触发点，早于实际切换）
  → context_switch()
      → switch_to()
          → __switch_to_asm()      （汇编，切换通用寄存器）
          → __switch_to()          （C 函数）
              → switch_fpu_prepare()
                  → save_fpregs_to_fpstate()   ← 挂载点
                      → XSAVEOPT/XSAVES
```

内核原生的 `x86_fpu:x86_fpu_after_save` tracepoint 仅在 `fpu_sync_fpstate()`（ptrace/signal/core dump 场景）中触发，不覆盖常规调度路径。`save_fpregs_to_fpstate()` 是常规调度路径的必经函数，且为独立符号（非内联），可直接挂 kprobe/kretprobe。

### 4\.2 实现要点

1. **entry/return 关联**：kretprobe 无法直接获取原始入参，需在 kprobe entry 阶段将 `struct fpu *`（`arg0`）按线程 ID（`tid`）存入临时 map，kretprobe 阶段据此取回。

2. **进程过滤**：在 kprobe entry 阶段以 `comm == "llama-server"` 过滤，避免统计系统噪音进程。

3. **数据读取**：在 kretprobe（保存动作已完成）阶段读取 `((struct fpu *)@start[tid])->fpstate->regs.xsave.header.xfeatures`，即 `XSTATE_BV`。

4. **分类计数**：按位掩码判断具体分量（AVX / opmask / ZMM\_Hi256 / Hi16\_ZMM），以及综合掩码 `0xe4` 判断是否属于向量相关切换。

5. **按 CPU 分布**：额外记录每个逻辑 CPU 上的事件数，用于观察是否存在核间迁移导致的额外开销。

## 脚本文件

```SQL
#!/usr/bin/env bpftrace

/*
 * x86 V-state save/restore 综合观测脚本
 * - 按 xfeatures 位图细分各分量(AVX/OPMASK/ZMM256/ZMM16)的save次数
 * - 按"这次切换是否触发了save"分类统计切换耗时
 * - restore独立计数(不参与耗时分类,理由见之前讨论: restore发生在
 *   返回用户态前,时序上跟"这次switch的A-B区间"不是同一个窗口)
 * - 全程按 comm == "llama-server" 过滤,避免系统噪音污染统计
 */

BEGIN {
    printf("Tracing x86 V-state save/restore + context switch overhead...\n");
    printf("Filtering on comm == \"llama-server\"\n");
}

/* save 探测 entry：记录 fpu 指针 */
kprobe:save_fpregs_to_fpstate
/comm == "llama-server"/
{
    @fpu[cpu] = arg0;
}

/* save 探测 return：解析 xfeatures，做分量拆解，并标记本次切换 save 发生 */
kretprobe:save_fpregs_to_fpstate
/@fpu[cpu]/
{
    $fpu = (struct fpu *)@fpu[cpu];
    $xf = $fpu->fpstate->regs.xsave.header.xfeatures;

    @saves_total = count();
    @save_happened[cpu] = 1;

    if ($xf & 0x04) { @avx_saves = count(); }
    if ($xf & 0x20) { @opmask_saves = count(); }
    if ($xf & 0x40) { @zmm256_saves = count(); }
    if ($xf & 0x80) { @zmm16_saves = count(); }
    if ($xf & 0xe4) { @vec_saves = count(); }

    delete(@fpu[cpu]);
}

/* restore 探测：独立计数，不参与耗时分类 */
kprobe:restore_fpregs_from_fpstate
/comm == "llama-server"/
{
    @restore_count = count();
}

/* 点A：切出阶段，记录起点时间戳 */
tracepoint:sched:sched_switch
/args->prev_comm == "llama-server"/
{
    @start_ns[cpu] = nsecs;
    @save_happened[cpu] = 0;
}

/* 点B：切入完成，按 save_happened 分类耗时 */
kprobe:finish_task_switch.isra.0
/@start_ns[cpu]/
{
    $delta = nsecs - @start_ns[cpu];

    if (@save_happened[cpu]) {
        @with_save_total = @with_save_total + $delta;
        @with_save_count = count();
    } else {
        @without_save_total = @without_save_total + $delta;
        @without_save_count = count();
    }

    delete(@start_ns[cpu]);
    delete(@save_happened[cpu]);
}

END
{
    clear(@fpu);
    printf("\n========== [1] save 分量拆解 (xfeatures 位图) ==========\n");
    printf("save 总次数:      "); print(@saves_total);
    printf("向量相关(0xe4):   "); print(@vec_saves);
    printf("  avx (bit2):     "); print(@avx_saves);
    printf("  opmask (bit5):  "); print(@opmask_saves);
    printf("  zmm256 (bit6):  "); print(@zmm256_saves);
    printf("  zmm16 (bit7):   "); print(@zmm16_saves);

    printf("\n========== [2] 切换耗时 (以 save 是否发生分类) ==========\n");
    printf("有 save 的切换 - 次数:      "); print(@with_save_count);
    printf("有 save 的切换 - 总耗时(ns):"); print(@with_save_total);
    printf("无 save 的切换 - 次数:      "); print(@without_save_count);
    printf("无 save 的切换 - 总耗时(ns):"); print(@without_save_total);

    printf("\n========== [3] restore 独立计数 ==========\n");
    printf("restore 总次数: "); print(@restore_count);
}
```

## 测试及结果

启动server命令行如下，使用taskset限制四个核，设置为四并发，使用 3b 模型，在WSL2下运行，使用CPU核心为AMD Ryzen 7 8745H \(16 核, AVX\-512\)。

```C
LD_LIBRARY_PATH="$PWD/bin" \
  taskset -c 12-15 bin/llama-server \
    -m ~/test/llama-3.2-3b-instruct-q4_k_m.gguf \
    -t 4 -tb 4 \
    --parallel 4 -c 2048 --cont-batching --port 8080
```

运行结果如下：

x86 vs RISC\-V 对比

相较于同等测试条件下在 RISCV 板卡上的测试数据，x86架构下的保存次数极少，这是由于实验平台性能差异造成的：测试是在windows主机中的WSL中进行的，CPU性能优势使得WALL TIME大幅降低，继而使得线程切换次数大幅减少，所以最终结果有明显差异。

此外可以观察到每次调用`save_fpregs_to_fpstate()`时，bit5和bit7位恒为1，而bit2/bit6 只有三成左右的时候为1，一个可能的原因是：ggml的 AVX\-512 GEMM kernel 在每次调用结束时被编译器插入了`vzeroupper`，导致bit2/bit6频繁被清零，只有在两次调度切换之间又执行了一段新的向量代码时才会重新变回1；而掩码寄存器\(bit5\)和ZMM16\-31\(bit7\)一旦被用过一次，没有对应的自动清空机制，会一直保持"曾用过"的状态，因此稳定在100%。
