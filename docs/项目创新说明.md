# 项目创新说明

## 1. 证伪向量保存为主要瓶颈

赛题把优化目标放在减少 RVV 向量状态的保存和恢复。本项目在 `sched:sched_switch` 上用 bpftrace 读取 `pt_regs.status` 的 VS 域，按 CPU 和线程统计 Dirty-V 的保存与恢复，并和同一次运行的吞吐、TTFT 放在一起比较。测得 V 状态切换的额外开销约 0.2%（口径待补：相对哪一段推理时间、如何从 trace 算出）。

六种绑核和调度策略下，保存次数可以相差数倍，吞吐仍在同一量级。`tests/test/group6/` 中，3B 模型、4 线程、核 4–7：`taskset` 约 4.1 万次保存、聚合吞吐 2.86；`taskset` 加 `SCHED_FIFO` 约 6300 次保存、吞吐 2.72。保存次数降到约六分之一，吞吐没有上升。`group3` 同样是保存明显下降、吞吐略降。

推理线程已经占住目标核时，V 状态保存次数不是吞吐的代理指标。有干扰时吞吐下降，损失的是推理线程让出核心后的计算时间。

## 2. 推理感知的核心隔离

`taskset` 和 cgroup 按进程绑核，会把 llama-server 里负责网络和组 batch 的线程一起绑上。`vec_affine_sched` 用 uprobe / uretprobe 挂在 `libggml-cpu.so` 的 `ggml_compute_forward_mul_mat` 上，把执行过矩阵乘的 worker 放到 CPU 0–3，其余任务放到 CPU 4–7。不改 llama.cpp，也不重编内核。这里对应 K1 的 cluster0（带 IME）和 cluster1。

推理线程时间片 30ms，普通任务 2ms；推理线程被唤醒时插入本核队列头部。原核空闲时优先回到上次运行的核。

`tests/sched_ext/`：无额外干扰时，CFS 聚合吞吐 6.81，本方案 6.88。高负载下 CFS 为 1.76，4ms/20ms 的旧方案为 1.86，2ms/30ms 为 3.34，吞吐约提高 90%，平均 TTFT 从 4298ms 降到 2880ms。只换 sched_ext、时间片仍是 4ms/20ms 时，高负载吞吐与 CFS 接近，时间片比例是这套隔离里起作用的部分。
