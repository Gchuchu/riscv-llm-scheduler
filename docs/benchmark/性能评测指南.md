# 性能评测指南

本文说明 `src/benchmark/benchmark_llama.py` 的通用 benchmark 用法、自动化实验矩阵、指标边界和结果文件。脚本支持 QEMU、本机、远程板卡等普通测试；1B/3B/8B 与 3B 并发扫描只是其内置的两组自动化实验。

`src/benchmark/bench_runner.py` 和 `bench_runner_all.py` 是独立工具，不属于本文范围，也不应按本文修改。

## 1. 两种工作方式

| 工作方式 | 适用场景 | server 生命周期 | 结果粒度 |
|---|---|---|---|
| 普通 benchmark | QEMU 验证、已有 server 的本机/远程性能测试、自定义并发与 prompt | 用户自行启动、停止和配置 server | 每个 warmup/trial 一行的聚合 CSV |
| 自动化实验矩阵 | 固定的模型规模和并发扫描实验 | 脚本经 SSH 启动、等待、停止它自己创建的 server | 每轮汇总 CSV + 每请求 CSV + 完整 server 命令 |

普通模式不会替用户管理 server。自动化矩阵只在 `--mode remote` 下启用，并且只管理本工具启动的进程；默认拒绝停止已经运行的其他 llama-server，除非显式传入 `--replace-existing-server`。

## 2. 依赖与环境

客户端需要 Python 3、`requests`、`numpy`：

```bash
pip install requests numpy
```

V-state 采集是可选项。需要 bpftrace、足够权限、可用的内核 BTF，以及与板卡内核匹配的追踪脚本。远程模式通过系统 SSH 客户端连接板卡；`--ssh-user` 只指定用户名，不保存或读取密码。建议预先配置 SSH 密钥认证，避免交互式密码提示破坏自动化测试。

性能比较组还应固定并记录：板卡和 CPU、OS/内核、llama.cpp 提交版本、模型哈希、CPU governor、后台负载、网络拓扑、prompt、token 上限、线程、上下文、cache 和调度策略。QEMU 数据仅用于功能验证或补充分析，不能与真实 RVV 硬件性能混合统计。

## 3. 手工启动 server（普通模式）

普通 benchmark 先要求 server 已就绪。通用命令模板如下，具体选项以板卡上 `./llama-server-rvv --help` 为准：

```bash
./llama-server-rvv -m <模型绝对路径>.gguf \
  --host <监听地址> --port <端口> \
  -c <总上下文> --parallel <slot 数> \
  [-t <推理线程数>] [-tb <批处理线程数>] [-lv <日志等级>] \
  [cache/绑核/调度等其他固定参数]
```

板卡的实际启动命令示例：

```bash
./llama-server-rvv -m Llama-3.2-3B-Instruct-Q4_K_M.gguf \
  --port 8080 -c 8192 --host 0.0.0.0 --parallel 8 -lv 4
```

### 服务端参数

| 参数 | 含义 | 评测要求 |
|---|---|---|
| `-m <file>` | GGUF 模型文件 | 记录绝对路径、文件名、量化格式、SHA-256。|
| `--host`、`--port` | HTTP 监听地址和端口 | 与客户端 URL 对应。远程访问通常使用 `0.0.0.0:8080`。|
| `-c <N>` | **总** context size | 不是单 slot context。必须记录并在对照组保持可比。|
| `--parallel <P>` | server slot 数 | 不是客户端线程数。改变 P 时应重启 server。|
| `-t <N>` | llama.cpp 推理计算线程数 | 不等于 client concurrency 或 slot 数；比较组固定。|
| `-tb <N>` | prompt/batch 阶段线程数 | 仅在当前二进制支持时使用；与 `-t` 分开记录。|
| `-lv <N>` | 日志等级 | 日志量可能影响环境，比较组保持相同。|
| cache 选项 | prompt/KV/RAM cache 策略 | 会改变重复 prompt 的时延；不能在对照组间混用。|
| `taskset`/cgroup/chrt 等 | 绑核与调度策略 | 是实验自变量的一部分，完整命令必须记录。|

本项目的标准并发扫描固定**每 slot context**。因此总 `-c` 必须随 `--parallel` 成比例变化：若每 slot 为 S，p2/p4/p8/p16 分别使用 `-c 2S/4S/8S/16S`。总 context 是由 slot 数派生的配置；这样每个 slot 的上下文资源一致，实验自变量仍是 `--parallel`。

启动后确认服务就绪：

```bash
curl -f http://<板卡 IP>:8080/health
```

## 4. 普通 benchmark 模式

### 4.1 三种运行模式

| `--mode` | 默认 URL | 用途 | 默认参数 |
|---|---|---|---|
| `qemu` | `http://127.0.0.1:18080/completion` | QEMU 端口转发、功能验证 | 并发 `2,4,8`，3 trials，3 rounds，32 tokens，超时 1800 s。|
| `local` | `http://127.0.0.1:8080/v1/chat/completions` | client 与 server 同机 | 并发 `2,4,8`，3 trials，3 rounds，128 tokens，超时 600 s。|
| `remote` | `http://<host>:8080/v1/chat/completions` | client 连接远程板卡 | 与 local 相同。|

`--url` 的优先级最高，可覆盖上述地址。`--port` 只覆盖 URL 端口。QEMU 的 `/completion` 与 local/remote 的 `/v1/chat/completions` payload 不同；自定义 URL 前应确认 API 兼容。

### 4.2 常用命令

QEMU 功能验证：

```bash
python src/benchmark/benchmark_llama.py --mode qemu --tag qemu_smoke
```

本机 server：

```bash
python src/benchmark/benchmark_llama.py \
  --mode local --pid <llama-server PID> \
  --concurrency 2,4,8 --rounds 3 --trials 3 \
  --streaming --server-params "-t 4 -tb 4 -c 8192 --parallel 8" \
  --tag local_baseline
```

local 模式默认只会查找进程名 `llama-server`。若二进制叫 `llama-server-rvv`，应显式传入 `--pid`，否则无法采集 RSS。

远程已有 server：

```bash
python src/benchmark/benchmark_llama.py \
  --mode remote --host <板卡 IP> --ssh-user root \
  --concurrency 2,4,8 --rounds 3 --trials 3 \
  --streaming --server-params "-t 4 -tb 4 -c 8192 --parallel 8" \
  --tag rvv_baseline
```

自定义接口：

```bash
python src/benchmark/benchmark_llama.py \
  --url http://<host>:<port>/v1/chat/completions \
  --concurrency 4 --rounds 5 --trials 3 --streaming \
  --tag custom_endpoint
```

`--compare` 会依次运行 `baseline`、暂停等待人工应用优化、再运行 `optimized`；它不会重启或重新配置 server。`--set-performance` 只设置运行 benchmark **客户端**的机器，remote 模式下仍须在板卡侧设置并验证 governor。

### 4.3 普通模式的请求与预热

每个 round 使用一个 `threading.Barrier`：所有 `--concurrency` 个 worker 都准备好后，客户端同时释放请求。它避免了线程创建期间第一个请求单独先到 server 的偏差，但网络和服务端接收仍可能有自然微差。

普通模式仍保留两层预热：

1. 所有档位前发送 1 条完整请求，不写 CSV。
2. 每个并发档位再跑 1 个 round，写入 CSV 为 `trial=0, is_warmup=True`，不进入正式汇总。

因此普通模式报告的是预热后的稳态结果，不应称为冷启动首请求延迟。请求失败会打印警告；若正式行的 `sample_count < concurrency x rounds`，应视为无效 trial，排查后重跑。

## 5. 自动化远程实验矩阵

自动化矩阵会经 SSH 运行以下流程：确认不存在冲突 server -> 启动指定模型 -> 等待 `/health` 最长 180 秒 -> 每轮用启动屏障并发释放 32 个请求 -> 停止 server。模型、server 参数、启动命令和请求结果会写入 CSV。

内置模型路径如下，使用模型规模选择即可，不需要重复填写 `-m`：

| 规模 | 板卡路径 |
|---|---|
| 1B | `/root/llama-3.2-1b-instruct-q4_k_m.gguf` |
| 3B | `/root/Llama-3.2-3B-Instruct-Q4_K_M.gguf` |
| 8B | `/root/Meta-Llama-3.1-8B-Instruct-Q4_K_M.gguf` |

### 5.1 矩阵命令

完整矩阵：

```bash
python src/benchmark/benchmark_llama.py \
  --mode remote --host <板卡 IP> --ssh-user root \
  --experiment-matrix full \
  --server-binary /root/llama-server-rvv \
  --server-threads 4 --server-context 4096 \
  --parallel-sweep-context-per-slot 1024 \
  --output-dir results
```

只跑 1B/3B/8B 的 p4 规模实验：

```bash
python src/benchmark/benchmark_llama.py \
  --mode remote --host <板卡 IP> --ssh-user root \
  --experiment-matrix model-scale --model-sizes 1,3,8 \
  --server-binary /root/llama-server-rvv \
  --server-threads 4 --server-context 4096 \
  --output-dir results
```

只跑 3B p2/p4/p8/p16，并固定每 slot context 为 1024：

```bash
python src/benchmark/benchmark_llama.py \
  --mode remote --host <板卡 IP> --ssh-user root \
  --experiment-matrix parallel-sweep \
  --server-binary /root/llama-server-rvv \
  --server-threads 4 --parallel-sweep-context-per-slot 1024 \
  --output-dir results
```

用 `--dry-run` 可只打印实验计划和将执行的 server 命令，不连接板卡。

### 5.2 固定实验内容

| 实验 | 模型 | server `--parallel` | 正式轮数 | 每轮客户端请求 |
|---|---|---:|---:|---:|
| `model-scale` | 1B、3B、8B | 4 | 每模型 1 | 32 |
| `parallel-sweep` | 3B | 2、4、8、16 | 每档 5 | 32 |

每一轮 32 个请求均由客户端启动屏障同时释放，服务端并发 slot 由 `--parallel` 控制。32 是单个并发突发请求数，不是“32 请求分成多个小批次”的普通模式语义。自动化矩阵没有额外 warmup；延迟、吞吐和 V-state 都覆盖同一批完整的 32 条请求。

`model-scale` 固定 p4、总 context、线程、prompt、cache、max tokens 和其他 server 参数，仅模型文件/规模变化。若需要与 parallel-sweep 的 p4 横向对照，应将它的 `--server-context` 设为 `4 x 每 slot context`。`parallel-sweep` 固定 3B、每 slot context、线程、prompt、cache、max tokens 和其他 server 参数，仅 `--parallel` 变化，总 context 由 parallel 派生。服务重启是切换模型或 parallel 的必要步骤，不构成额外实验变量。

矩阵强制使用流式请求以测量 Client TTFT。默认不设置 HTTP read timeout，允许 slot 排队较长的尾部请求完成；只有显式传入 `--timeout <秒>` 才限制单请求等待时间。

### 5.3 自动化模式参数

| 参数 | 说明 |
|---|---|
| `--experiment-matrix full|model-scale|parallel-sweep` | 启用自动化矩阵。仅 remote 模式可用。|
| `--server-binary` | 板卡 server 绝对路径，默认 `/root/llama-server-rvv`。|
| `--server-lib-dir` | 必要时设置板卡 `LD_LIBRARY_PATH`。默认继承板卡环境。|
| `--server-threads` | 自动化 server 的 `-t` 和 `-tb`，默认 4。|
| `--server-context` | model-scale 的 `-c`，默认 2048。若要与 parallel-sweep 的 p4 对照，应设置为 `4 x 每 slot context`。|
| `--parallel-sweep-context-per-slot` | parallel-sweep 必填。固定每个 slot 的 context，脚本自动计算 `-c = 每 slot context x parallel`。|
| `--server-extra-args` | 以 shell 参数串追加到 server 命令，例如 `--server-extra-args="--no-mmap"`。|
| `--disable-prompt-cache` | 显式追加 `--no-cache-prompt --cache-ram 0`，形成独立的 cache-off 实验。默认保留 server 原有 cache 行为。|
| `--model-sizes` | 规模实验选择 `1,3,8` 中的一部分。|
| `--vstate-script` | 板卡 bpftrace 脚本路径，默认 `/root/vstate_trace.bt`。|
| `--replace-existing-server` | 允许停止非本工具启动的 server，具有破坏性；共享板卡默认不要使用。|
| `--print-warmup-requests` | 额外打印被显式标为批内 warmup 的请求。|
| `--print-response-text` | 在终端输出响应正文。默认关闭，正文仍保存到逐请求 CSV。|
| `--response-print-limit` | 限制终端输出的单条响应字符数；0 表示不截断。|
| `--output-dir` | 自动化实验 CSV 目录，默认 `results`。|

## 6. 指标定义

| 指标 | 数据来源 | 含义与边界 |
|---|---|---|
| TPS | 客户端 | `成功返回的 completion token 总数 / 该轮完整挂钟时间`。包含服务端排队、推理和网络等待，不等于单请求 `predicted_per_second`。|
| Client TTFT | 客户端 | 流式时，从 HTTP 请求开始到首个含 `delta.content` 的 SSE 事件；含网络、server 接收/排队、prompt 和首 token 生成。非流式时等于 E2E。|
| Prompt Ms | server API | `timings.prompt_ms`。代表 llama-server 报告的 prompt 阶段；流式响应未提供 timing 时为 0，应解读为不可得。|
| Server TTFT | server API 语义 | 当前脚本将有效的 `prompt_ms` 记为 `server_ttft_ms`，表示 server 从开始 prompt 处理到开始生成的时间，不含进入 slot 前的 HTTP 排队。|
| Queue+Net | 推导值 | `max(0, Client TTFT - Server TTFT)`。用于观察客户端等待与传输量级；它不是纯排队时间，仍混有网络、首 token 和 API 行为。|
| E2E | 客户端 | HTTP/SSE 请求开始到完整响应结束，含网络、排队、prompt 和生成。|
| P95 | 原始样本 | 正式样本的 95 分位。终端汇总跨正式 trial 池化；不要把多个 trial 的 P95 再求平均。|
| V-state | bpftrace | 基于 `sched_switch` 时任务 V 状态推断的 save/restore 次数。是频次，不是硬件时延。|

不要依据时延高低筛掉“异常”成功请求。缓存命中、slot 排队、请求完成顺序不同都是需要保留和解释的真实现象。

## 7. V-state 采集范围

自动化矩阵每个 32 请求轮次单独启动一个 bpftrace，轮次结束时停止追踪并读取完整 `END` 汇总。因此该轮的 V-state 计数覆盖整轮所有已提交请求，保存为共享轮次数据，而非 32 条逐请求数据。自动化矩阵不排除批内 warmup，保证 V-state、吞吐与延迟的样本范围一致。

普通模式在整个 benchmark 过程中持续追踪，并从最近累计快照计算 trial 差分，边界精度较自动化矩阵低。无论哪种模式，V-state 结果都有以下限制：

- 不能把一个轮次的 save/restore 次数分配给某条具体 HTTP 请求。
- 追踪依赖 bpftrace 权限、BTF、`task_struct`/内核栈布局和输出格式；更换内核、板卡或厂商补丁后必须重新校验。
- 进程专属统计依赖进程名匹配 `llama-server`，同时应保留全系统计数。
- save/restore 次数不能推出微秒级切换开销；单次时延需要独立的内核级时间戳方案。

若 bpftrace 不可用或字段为空，标记为“未采集/待校验”，不要用 0 代替缺失值。

## 8. 输出文件与复现

普通模式在当前工作目录生成：

```text
benchmark_<tag>_<YYYYMMDD_HHMMSS>.csv
```

该文件按 warmup/trial 聚合。普通模式的 `--server-params` 只是用户提供的文字描述，会写入 CSV；请完整填写手工启动参数。

自动化矩阵在 `--output-dir` 中生成同一时间戳的两份文件：

```text
rvv_experiment_<timestamp>_rounds.csv
rvv_experiment_<timestamp>_requests.csv
```

`rounds.csv` 包含每轮的汇总性能和共享 V-state 计数；`requests.csv` 包含每条请求的 request ID、完成顺序、TTFT、Prompt Ms、Server TTFT、Queue+Net、E2E、TPS、token 数和响应正文。两者都包含 model path、server binary、`--parallel`、线程、context、context/slot、额外参数、完整 server command、启动时间、host、prompt 和 token 上限。

正式统计应只纳入完整成功轮。对自动化矩阵，默认要求每轮 `sample_count = 32`；对普通模式，要求 `sample_count = concurrency x rounds`。原始 CSV、服务端日志、bpftrace 脚本版本和环境信息应按 `tag` 或时间戳一起归档。

## 9. 提交结果前检查

1. 区分普通模式和自动化矩阵，未把两者的预热、并发与输出语义混用。
2. 对照组的模型哈希、完整 server 命令、prompt、max tokens、cache、governor、上下文和调度策略一致。
3. 自动化 p2/p4/p8/p16 使用一致的每 slot context、线程、prompt、cache 和 token 上限；总 context 按 parallel 自动派生。
4. Client TTFT、Server TTFT、Queue+Net、E2E 分开解释，未把 `Queue+Net` 误写成纯排队时间。
5. 无 HTTP 超时、失败样本或不完整请求数；否则保留原始记录并重跑该轮。
6. V-state 明确为轮次级共享计数，未解释为逐请求数据或微秒级开销。
