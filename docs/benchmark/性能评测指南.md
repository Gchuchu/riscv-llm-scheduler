# 性能评测方法与指标

- 以llama.cpp server 模式为基准。
- 评测指标：吞吐(TPS)，首 token 延迟(TTFT)，端到端延迟(E2E)，服务端 prompt 时间，P95 尾延迟，V 状态切换开销。
- CPU频率：策略需要固定为`performance governor`
- 评测次数：每组配置至少重复 3 次，报告均值与标准差
- 控制变量：相同模型与量化版本、相同 --threads 参数、相同输入长度分布。
- 模型要求：使用不超过 3B 参数量的量化模型（如Llama-3.2-1B/3B Q4_K_M）

## 评测指标

### 吞吐量（TPS）

每秒生成的 token 数。衡量推理服务的整体处理能力。

```
TPS = total_tokens / wall_time_seconds
```

### TTFT（Time To First Token，首 token 延迟）

客户端测量的首 token 延迟（ms）。反映用户感知的响应速度。

| 模式 | 含义 |
|---|---|
| `--streaming`（推荐） | 首个 SSE `data:` 事件到达时间 |
| 非流式（默认） | = E2E（全部 token 一次性返回，无独立首 token 事件） |

### Prompt Ms（服务端 prompt 处理时间）

服务端 `timings.prompt_ms`，反映 prompt eval 耗时（ms）。剔除网络和排队影响，可用于评估 RVV 对 prompt 处理的加速效果。

### E2E（End-to-End 延迟）

客户端完整请求耗时（ms），含网络 + 排队 + prompt eval + token 生成全过程。

### P95 尾延迟

跨所有 trial 池化后计算的 95 分位值。样本量 = concurrency × rounds × trials。

## 测试方法

### 评测基准

- 推理框架：llama.cpp server 模式
- 模型：Llama-3.2-1B/3B Q4_K_M 量化模型
- 并发场景：2、4、8 并发请求

### 基线配置

- 相同模型与量化版本
- 相同 `--threads` 参数
- 相同输入长度分布
- CPU 频率策略固定为 `performance` governor

### 数据采集

- 每组配置**至少重复 3 次**
- 报告均值与标准差
- P95 跨 trial 池化计算（非 mean-of-P95）
- 每个并发档位会先跑一轮预热（记录为 trial=0, is_warmup=True），不参与统计

### 环境区分

- **性能数据**：须来自真实 RVV 1.0 硬件
- **QEMU 数据**：仅作功能验证或补充分析，与真实硬件数据分开呈现

## 脚本使用说明

测试脚本 `src/benchmark/benchmark_llama.py` 用于自动化采集并输出结构化结果。

### 运行模式

| 模式       | 适用场景       | 用法                          |
|:--------:| ---------- | --------------------------- |
| `qemu`   | QEMU 虚拟机验证 | `--mode qemu`               |
| `local`  | 板子本地运行     | `--mode local`              |
| `remote` | 宿主机连远程板子   | `--mode remote --host <IP>` |

### 快速开始

```bash
# QEMU 验证
python benchmark_llama.py --mode qemu --tag baseline

# 板子本地（流式测真实 TTFT）
python benchmark_llama.py --mode local --streaming --rounds 3 --trials 3

# 远程板子（流式测真实 TTFT）
python benchmark_llama.py --mode remote --host 192.168.1.100 --streaming
```

### 关键参数

| 参数 | 说明 | 默认值 |
|---|---|---|
| `--concurrency` | 并发数，逗号分隔 | `2,4,8` |
| `--trials` | 每档重复次数 | `3` |
| `--rounds` | 每 trial 内重复批次数。样本数 = concurrency × rounds | `3` |
| `--streaming` | 流式请求，测客户端真实 TTFT。不加时 TTFT=E2E | 否 |
| `--tag` | 测试标签（baseline/optimized 等） | 模式名 |
| `--compare` | 一键对比模式（自动跑 baseline + optimized） | — |
| `--max-tokens` | 每请求最大生成 token 数 | 32(qemu) / 128 |
| `--timeout` | 请求超时（秒） | 1800(qemu) / 600 |
| `--set-performance` | 固定 CPU governor 为 performance | — |
| `--ssh-user` | 远程模式 SSH 用户名，用于 V state 采集 | 当前用户 |

### 输出

- **终端**：每轮实时输出 + 最终汇总报表（均值 ± 标准差，P95 为跨 trial 池化值）
- **CSV**：`benchmark_标签_时间戳.csv`，含 TPS、TTFT、Prompt Ms、E2E 及 V state 字段

### CSV 字段说明

| 字段 | 含义 | 来源 |
|---|---|---|
| `throughput_tps` | 系统吞吐量 (token/s) | `total_tokens / wall_time` |
| `avg_ttft_ms` | 平均首 token 延迟 (ms) | 客户端：流式=首个 SSE 事件，非流式=E2E |
| `p95_ttft_ms` | 首 token 延迟 P95 (ms) | per-trial 样本池化 |
| `avg_prompt_ms` | 平均服务端 prompt 处理 (ms) | 服务端 `timings.prompt_ms` |
| `p95_prompt_ms` | 服务端 prompt 处理 P95 (ms) | per-trial 样本池化 |
| `avg_e2e_ms` | 平均端到端延迟 (ms) | 客户端 `time.time() - req_start` |
| `p95_e2e_ms` | 端到端延迟 P95 (ms) | per-trial 样本池化 |
| `wall_time_s` | 该 trial 挂钟时间 (s) | batch 开始到结束 |
| `sample_count` | 该 trial 样本数 | `concurrency × rounds` |
| `is_warmup` | 是否预热轮 | True/False |
| `vstate_save_count` | V 状态保存次数（全系统） | bpftrace 采集 |
| `vstate_restore_count` | V 状态恢复次数（全系统） | bpftrace 采集 |
| `vstate_llama_save` | V 状态保存次数（llama-server 进程） | bpftrace 采集 |
| `vstate_llama_restore` | V 状态恢复次数（llama-server 进程） | bpftrace 采集 |

> **注意**：终端的 P95 是跨所有 trial 池化后的值（更准确），CSV 中的 P95 是单 trial 的。报告以终端为准。

### 指标说明

| 指标 | 含义 |
|---|---|
| **TPS** | 吞吐量（token/s），越高越好 |
| **TTFT** | 客户端首 token 延迟（ms）。流式 = 首个 SSE 事件时间，非流式 = E2E |
| **Prompt Ms** | 服务端 prompt eval 时间（ms），剔除网络/排队 |
| **E2E** | 客户端端到端延迟（ms），含网络 + 排队 + 推理全过程 |
| **P95** | 跨 trial 池化 95 分位值 |
| **V State** | V 状态 save/restore 频次计数，依赖 bpftrace。仅反映切换频次，不含精确耗时（μs 级测量需改内核） |

## 测试中遇到的问题

### OpenKylin 无 bpftrace

OpenKylin 软件源未收录 bpftrace（`apt install bpftrace` 报无可用包）。从 QEMU openEuler（源内置 bpftrace-0.19.1）编译后 scp 到板子可运行，但 OpenKylin 内核未开启 `CONFIG_DEBUG_INFO_BTF`，bpftrace 无法解析内核结构体：

```
ERROR: Cannot resolve unknown type "struct task_struct"
```

V state 追踪需要 BTF 支持。Bianbu OS 可安装 `linux-image-*-dbg` 后通过 `pahole` 生成 BTF 解决。建议换用 Bianbu OS 进行 V state 相关测试。

### benchmark 读取 bpftrace 输出的问题

benchmark 通过 SSH 远程读取 `/tmp/vstate.txt` 文件，按行解析 llama-server 线程的 save/restore 计数。存在以下问题：

- **行截断**：8 个 llama-server 线程各有 save 和 restore 行，加上全系统总数 2 行共 18 行。`grep | tail -20` 在输出过大时可能截断部分线程数据，导致 llama-server 的 restore 计数漏采或偏低。
- **文件缓冲**：bpftrace 的 `-o` 重定向使用 C 库全缓冲，运行时读文件可能拿到过期数据。当前通过 `stdbuf -oL` 强制行缓冲缓解，但 `stdbuf` 非 POSIX 标准，部分系统可能缺失。
- **时间对齐**：per-trial V state 数据基于 interval:s:1 输出读取，与 benchmark 的 trial 起止时间不完全对齐，精度约为 ±1s。
