## 1 赛题解析

### 1.1 背景

LLM 推理是典型的高强度矩阵向量乘，llama.cpp 已经完成 RVV 1.0 的适配。

### 1.2 问题

**RVV 寄存器状态开销**

在 RISC-V 架构中，每个 hart 拥有 32 个向量寄存器（v0–v31），单次完整 V 状态保存需要 512 字节至 1024 字节以上的内存写入。Linux 通过 VS 状态位配合惰性上下文管理策略（lazy save / restore）降低不必要的状态切换开销，但在多向量密集型线程并发运行时，当向量状态为 dirty 的线程被抢占，仍会触发 V 寄存器组的完整保存。

**默认调度策略的不足**

在推理服务器同时处理多个并发请求时，Linux 默认调度策略（CFS）对向量密集型推理线程与普通线程一视同仁，导致：
- 推理线程在计算关键路径上被频繁抢占
- 积累的 V 状态切换开销造成整体吞吐下降
- 尾延迟（P95 TTFT）恶化

## 3 环境搭建

**负责人**：@陈子轩 @郭恒

参考链接：
- [llama.cpp + SpaceMit 参考](https://github.com/ggml-org/llama.cpp/blob/master/docs/build-riscv64-spacemit.md)
- [openEuler + QEMU 参考](https://www.openeuler.org/zh/blog/phoebe/2023-09-26-Run-openEuler-RISC-V-On-Qemu.html)

**目标**：能在 RISC-V 上运行 llama.cpp 推理

步骤：
1. 安装 openEuler 24.03 镜像（下载）
2. 安装 RISC-V 交叉编译工具链
3. 配置 RISC-V 环境
4. 交叉编译 llama.cpp（RVV 1.0 支持）
5. 下载量化模型（Llama-3.2-1B/3B Q4_K_M）
   - [1B 模型](https://huggingface.co/Solshine/Llama-3.2-1B-Q4_K_M-GGUF/tree/main)
   - [3B 模型](https://huggingface.co/aashish1904/Llama-3.2-3B-Q4_K_M-GGUF)
6. QEMU 启动 RVV 内核：`qemu-system-riscv64 -cpu rv64,v=true,vlen=256`

**路线选择**：
- **路线1**：模拟 openEuler 系统，其上运行 llama.cpp 【赛题要求】
- **路线2**：QEMU 直接运行 llama.cpp 【暂不做】

工具：显存计算 https://app.linpp2009.com/zh/llm-gpu-memory-calculator/llama

## 4 解决方案

### 4.1 量化工具（对应评分 10 分）

- eBPF 程序（参考 bpftrace）：kprobe 挂载 `riscv_vstate_save`
- 统计：调用频次、每次耗时、dirty V 被抢占事件
- QEMU 上验证可采集数据
- 输出：V 状态切换开销与并发数、模型规模的量化关系

### 4.2 调度优化（对应评分 15 分）

**保底方案（必做）**
- CPU affinity：推理线程绑定指定核心
- cgroup cpuset：限制推理服务使用指定核心
- QEMU 验证绑定生效

### 4.3 性能评测（对应评分 10 分）

- benchmark 测试脚本
- 2、4、8 并发场景：优化前 vs 优化后
- 每组重复 3 次，记录均值与标准差
- 输出：TPS、平均 TTFT、P95 TTFT

### 4.4 技术报告（对应评分 40 分）

- **设计方案**：问题分析 + 优化方案 + 与 CFS/lazy save 的关系
- **实现方案**：架构图/流程图 + 相关工作调研与引用
- **实验结果**：数据表格 + 环境说明 + 基线配置
- **特色创新**：新调度原语 / 用户态-内核协同机制 / 深层分析

### 4.5 开发过程（对应评分 20 分）

- Git 提交历史规范、信息清晰
